01 / The instrument

Most agent evaluations are a measurement taken once. This one is a fixed instrument pointed at the same tasks night after night, so the question shifts from how good is this model to did anything change since yesterday. Five design decisions make that question answerable:

  • Deterministic checkers. Every task ends in a state assertion over a mock backend or an equality check against expected outputs. No LLM judges anywhere in a checker, so a task's verdict cannot drift between nights. Any movement is the model or the serving stack.
  • Paired models. Every queued task runs once on each agent model, adjacent in the queue, so the two are measured under the same conditions in the same batch.
  • Repetition. Tasks repeat within a batch, which is what makes within-night variation measurable at all.
  • Serving metadata. Every turn records stop_reason, the served_model the API reported, and the request_id, so a future change in pass rate can be tied to a serving change rather than guessed at.
  • Unattended and capped. A spend ledger, a nightly cap, a total cap and a dead-man switch. The harness fails toward not spending.

Everything it produces is public: the full trace of every episode, the label on every failure, and the ledger that every figure on this page is computed from.

02 / The first read: nothing has drifted

For each task-model pair seen in at least three batches, we test whether its pass rate is the same in every batch (permutation test, uncorrected). Across 42 pairs, three come out below p = 0.05. Chance alone produces about 2.1.

So the honest headline is a null: over two weeks and 5,647 episodes, per-task pass rates look stable, and outcomes behave like independent draws with a fixed per-task bias. That is worth saying plainly, because the instrument was built to catch the opposite, and it is the baseline any future drift has to beat.

A null result at this size is not proof of stability. Eight batches over fifteen days is thin, and two of those batches are from a single day. The test has the power to catch a large, sudden shift — a model swap behind the same name — and not much more. Detecting a slow drift needs months of nights, which is exactly what the instrument is for.

03 / Where the variance actually comes from

Run one task on one model several times in the same batch and you get a cell. A cell is mixed when the same prompt, unchanged, both passed and failed inside that batch. On the active task set, nearly half of all cells are mixed — which sounds alarming until you ask which tasks are in that set.

Tasks are retired from the queue once no model fails them, so the active set is, by construction, the tasks whose pass rates sit away from the extremes — and a task at a 50% pass rate produces a mixed cell almost every time it repeats. The 0% on the left is the control: when a task is easy for both models, repetition produces the same answer every time. Most of the mixedness on the right is our task selection, not a property of the models.

What survives that correction is still useful to anyone choosing an eval budget: on tasks at the edge of a model's ability, a single run is close to a coin flip, and the ordering of two models on one such task can invert between runs. The lesson is about how to measure, not about a hidden instability in the models.

04 / Two models, same 22 tasks

The paired design makes the model comparison cheap and fair: same tasks, same batch, same conditions.

The gaps are not a smooth ranking. Haiku never passes ops_stack_night_shift or cal_stack_week_planner in 84 attempts, and passes hard_csv_strict 4 times in 266, while Sonnet clears each at 98% or better. Yet Haiku is the better model on three tasks, including a TTL cache simulation it passes 92% of the time against Sonnet's 75%. These tasks were written to be hard for the stronger model, so this is the frontier of difficulty for these two, not a capability estimate.

05 / How agents fail

Coding failures are labeled by rerunning the submission: the first wrong case decides, with no model involved. Tool failures go to Claude Opus 5 with the trace and a replay diff against the reference solution, into a fixed nine-label taxonomy.

Tool-failure labelSonnet 5Haiku 4.5

Across 497 labeled tool failures there is not one hallucinated tool call and not one loop. These agents fail by misreading the policy they were given. Sonnet's characteristic failure is its own: it does the work, then stops before the confirmation message the task required.

One caveat sits on this whole section. The labels come from a single model. When Haiku 4.5 labeled the same 101 failures, it agreed with Opus on 45 of 70 (64%), and the disagreements clustered on one distinction — acting on the wrong entity versus misapplying a rule that led there. A human-labeled subset is the next validity step, and until it exists these counts describe one labeler's reading.

At less than half the pass rate, Haiku is still the cheaper route to a passing episode — but only where a checker can tell a pass from a failure and retries converge. On the tasks it almost never passes, they never converge and its expected cost is unbounded.

07 / What would change these numbers

The instrument is built; the evidence is young. In order of how much each would change what we can claim:

  • Nights. Nothing substitutes for elapsed time. Detecting serving drift needs dozens of separated batches, not a big single day.
  • A permanent control tier. Keep a sample of saturated tasks in the nightly queue so the selection effect in section 03 is measured continuously rather than argued about.
  • A model from another provider. Two Claude models make this a study of one family. A third breaks that.
  • Human labels. A hand-labeled subset turns the taxonomy from one model's opinion into a measured instrument.

All of it lands in the same public corpus as it arrives. The dataset and the dashboard update as the nights accumulate.
